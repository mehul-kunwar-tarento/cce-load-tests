# Implementation Plan: CCE performance testing setup (restructure)

**Branch**: `000-performance-testing-setup` (folder only; no git operations, D1) · **Date**: 2026-11-05 ·
**Spec**: [spec.md](spec.md) · **Tasks**: [tasks.md](tasks.md)

## 0. Summary and technical context

| Item | Value |
|---|---|
| Load generator | k6 2.3.0 + xk6-kafka 2.2.0 in Docker image `cce-load-tests/k6:2.3.0-kafka2.2.0` (`docker/k6/Dockerfile`) |
| Helper language | Node.js 22, ESM (`"type": "module"` in `package.json`; Node files use `.mjs`, k6 files use `.js`) |
| Runtime dependencies | `pg` (Postgres), `kafkajs` (Kafka admin: lag, offsets, consumer group). Nothing else at runtime. |
| Dev dependencies | `eslint`, `@eslint/js`, `globals`, `prettier`. ShellCheck through `docker run koalaman/shellcheck:v0.10.0` when not installed. |
| Testing | `node --test` with fixtures and mocks (unit), `k6 inspect` in the image with `--network none` (k6 scripts), `bash -n`, `docker compose config` (monitoring), JSON parsing |
| Target platform | Linux laptop with Docker (k6 container, `--network host`); Dev/UAT with k6 on a separate host |
| Systems under test | cce-collector-service, cce-matcher-service, cce-step-sla-service (release-2.0.0); protocol service only for plan-definition setup |
| Constraints | No state-changing git; no traffic or connection to any live system during the build (D14); no secrets in files; never prod |
| Project type | Test suite + CLI tooling, one repository, per-service folders copyable into the service repos |

**How the pieces fit** (one run):

```
scripts/run-test.sh local matcher stress
  └─ node tools/cli.mjs run local matcher stress
       1 resolve environment + settings (config/…, env vars, --set)  → results/<dir>/run-context.json
       2 preflight (tools/preflight)                                  → results/<dir>/preflight.json
       3 conditions: host, git commit, data volume, plan-definition set → result.conditions
       4 wait until the service is idle (service module)
       5 prepare (service module; e.g. Step SLA seeds alarms)          → results/<dir>/seed.json
       6 start metrics sampler + service watchers (Node)               → results/<dir>/watch-*.json, service-metrics.json
       7 docker run k6 (<service-folder>/tests/<subject>-<test-type>.test.js) → results/<dir>/k6-summary.json, k6.log
            ├─ runner polls the k6 REST API (JSON) → ctx.times.measureStart / sendEnd (§6.3 "k6 clock")
            └─ k6 → Prometheus remote write (tags testid/service/test_type/…) → Grafana
         (Step SLA, kind 'seeded': no k6; prepare() returned measureStart/sendEnd from the seed, §6.4)
       8 watchers run on until caught up / limit
       9 data checks (service module, SQL)                             → results/<dir>/data-checks.json
      10 build result (tools/core/result-builder)                      → results/<dir>/result.json
      11 render + print concise report (from result.json only)        → results/<dir>/report.md
      12 optional: compare with BASELINE                               → results/<dir>/baseline-comparison.json
```

Each spec folder has three files. The owner's required sections come first; the Spec Kit sections follow.

**`spec.md`** — header: `**Feature Branch**: n/a (folder only; suggested branch feature/<kebab-name>)`
(never an `NNN-name` branch: branches follow `02-naming-conventions.md`, `feature/…`, `chore/…`),
`**Created**`, `**Status**`, `**Input**`. Mandatory sections, in this order:
1. `## Goal` (what and why, 2–5 lines)
2. `## Scope` with `### In scope` and `### Out of scope`
3. `## Inputs` (settings, files, services, other packages' interfaces it consumes)
4. `## Outputs` (files, commands, JSON shapes, exit codes it produces)
5. `## Acceptance criteria` (numbered, each checkable statically per §12)
6. `## User Scenarios & Testing` (`### User Story N - <title> (Priority: P1|P2|P3)` with **Given/When/Then**, `### Edge Cases`)
7. `## Requirements` (`- **FR-001**: … MUST …`; unknowns `[NEEDS CLARIFICATION: …]`)
8. `## Success Criteria` (`- **SC-001**: …`)

**`plan.md`** — mandatory sections: `## Approach`, `## Files` (every file created/changed, one line each),
`## Interfaces` (exported signatures and JSON shapes, with the 000 plan section they implement), then
`## Technical Context`, `## Deviations / requests` (anything that differs from this 000 plan or needs a
change in a path the package does not own; "none" if none).

**`tasks.md`** — `- [ ] T001 [P] Description with exact file path`, phases Setup → Foundational → stories →
Polish → Verification; ticked `- [x]` when done. Tasks that cannot be done under the static-only rule (D14)
are written `- [ ] T0xx DEFERRED (owner): …` and are excluded from "every task ticked" (R13); they are
listed in docs/open-questions.md by C1.

C1's spec-index task checks every spec folder for these headings (a small node check, §12): presence,
not order; a leading section number (`## 3. Inputs`) is ignored when matching. The 000 blueprint carries
the same headings in `spec.md`; its `plan.md` maps them by section (Approach = §0, Files = §1, Interfaces =
§3–§9, Deviations = n/a) and the check accepts that mapping for `specs/000-performance-testing-setup/` only.

## 2. Naming conventions applied

### 2.1 Files and folders
| What | Rule | Examples |
|---|---|---|
| Folders | lowercase kebab-case, full words | `test-data/`, `plan-definition-sets/`, `unit-tests/` |
| Service folders | exactly the service repository name | `cce-collector-service/`, `cce-matcher-service/`, `cce-step-sla-service/` |
| k6 test scripts | `<subject>-<test-type>.test.js` | `collector-load.test.js`, `matcher-breakpoint.test.js` |
| Node test definitions (Step SLA, no k6) | `<subject>-<test-type>.test.mjs` | `step-sla-load.test.mjs` |
| Shared k6 modules | kebab-case noun | `lib/kafka-client.js`, `lib/thresholds.js` |
| Node modules | kebab-case noun, `.mjs` | `tools/core/result-builder.mjs` |
| Node unit tests | `<module>.spec.mjs` in a `unit-tests/` folder | `tools/core/unit-tests/settings.spec.mjs` |
| Shell scripts | kebab-case, verb first | `run-test.sh`, `check-services.sh`, `cleanup-test-data.sh` |
| Config | `config/environments/<env>.json` | `local.json`, `dev.json`, `uat.json` |

### 2.3 Test-data identifiers (D12)
- `runId`: default `yyyymmdd-hhmmss` local time of the run start (e.g. `20261105-142233`). A custom
  `RUN_ID` must match `^[A-Za-z0-9]{1,20}$` (**no hyphen**, no `_`/`%`, so `LIKE` needs no escaping);
  `validateRunId` accepts exactly `^\d{8}-\d{6}$` or that custom pattern. v1 run ids (`mmddHHMMSS`, 10
  digits) match the custom pattern and are treated as **legacy** by cleanup (§7.2).
- Test-data prefix: `LOADTEST-<runId>-` (`testDataPrefix`). **Run selectors always end with the id code**:
  `LOADTEST-<runId>-<idCode>-` for `idCode` ∈ {`col`, `mat`, `sla`} (per-run cleanup ORs the three;
  data checks use their own subject's). Because custom ids contain no hyphen and default ids are
  `d8-d6`, a selector of one run can never match another run's ids (`test` vs `test2`, `20261105` vs
  `20261105-142233`: the next segment differs). `--all` uses `LOADTEST-`. Cleanup also refuses a `--run-id`
  for which `results/` holds a different run id starting with `<runId>-` (belt and braces).
- Patient id (CloudEvent `subject`, `protocol_instance.patient_id`):
  `LOADTEST-<runId>-<idCode>-<phaseIndex>-<n>` where `phaseIndex` is the index of the phase in the phase
  plan (keeps warm-up and measure iterations distinct) and `n` is `exec.scenario.iterationInTest`
  (0-based, < the phase's `plannedEvents`). Ids are therefore **enumerable**: data checks and per-run
  cleanup generate the candidate ids from the phase plan (`generate_series`) and look them up through the
  unique `(cloudevents_id, source)` indexes instead of scanning with `LIKE` (§6.8, §7.2).
- Event id (CloudEvent `id`, `inbound_event_log.cloudevents_id`, `matcher_event_log.cloudevents_id`):
  `<patientId>-<stepNumber>` (1-based position in the journey; `1` for single-event tests).
  **Must be ≤ 50 characters** (collector limit): builders throw if longer. Default length: 9+15+1+3+1+1+1+9+2 ≤ 42.
- Correlation id: `LOADTEST-<runId>-corr-<n>`; facility id: dataset `facilityId` (default
  `LOADTEST-FACILITY-01`, overridable `FACILITY_ID`); CloudEvent `source`: dataset `source` (default
  `loadtest-emr`, overridable `EVENT_SOURCE`).
- Step SLA seeded patients: `LOADTEST-<runId>-sla-0-<n>`.
- Ids made by CCE applications (`protocol_instance.id`, `step_instance.id`, `step_sla_state_transition.id`,
  `deviation.id`) are UUIDv7 (time-ordered). `tools/core/run-id.mjs` exports `uuidV7Floor(date)` (48-bit ms
  timestamp, rest zero, e.g. `0192f3a1-2b3c-7000-8000-000000000000`) so queries can bound primary-key scans
  with `id >= $floor` (run start − 5 min). Seeded Step SLA rows get UUIDv7-shaped ids from the SQL
  expression `UUID_V7_SQL` exported by the same module (timestamp of `clock_timestamp()` + random bits),
  so the bound also holds for them (v1 seeded v4 ids).

### 2.4 Header comments (R11)

the dashboard `description`. FHIR fixtures: `$comment` is allowed and is stripped by

### 3.3 Resolution: one source of truth (D17)

```js
export function resolveSettings({ environment, subject = null, testType = null, breakpointKind = null,
                                 setContext = null, overrides = {}, env = process.env }) → ResolvedSettings
// subject/testType/breakpointKind are OPTIONAL: without all three (cleanup, preflight without --subject,
// plan-definitions) the result has values/sources/warnings only and derived.phasePlan = null.
// setContext (optional) = { expectedRows } from tools/plan-definitions, needed only to resolve STEP_SLA_PEAK_ALARM_RATE=auto.
// ResolvedSettings = { values: {NAME: typedValue}, sources: {NAME: 'default'|'environment'|'env-var'|'cli'|'derived'},
//                      derived: { phasePlan|null, stepSlaMaxWaitSeconds|null, … }, warnings: string[] }
export function printSettings(resolved, { onlyRelevant = true }) → string   // table: name, value (formatted), source, TBC flag
export function settingsForResult(resolved) → { NAME: { value, source } }  // what is saved
```

**`ResolvedSettings.values` types** (pinned; A1 and A2 code against this, k6 receives exactly these in

|---|---|---|
| `rate` | integer ≥ 1 | `LOAD_RATE: 50` |
| `duration` | number of **seconds** (may be fractional, e.g. `0.2` for `200ms`) | `LOAD_DURATION: 600`, `WARM_UP_DURATION: 0` |
| `list` (of rates) | `number[]`, strictly ascending | `LEVELS: [200, 400, 800]` |
| `boolean` | `true` / `false` | |
| `integer`, `number` | number | `MAX_DROPPED_RATE: 0.001` |
| `string`, `enum` | string | `CLEANUP_TEMP_INDEX: 'auto'` |

| `duration or auto` / `rate or auto` | resolved number (source `derived`) when `auto`; `null` only when it cannot be resolved without a subject/set | `STEP_SLA_MAX_WAIT: 10` |

- Parsing: `duration` through `lib/duration.js` `parseDuration` (throws on garbage: fixes v1's silent 0);
  `list` comma-separated; `boolean` `true/false/1/0`; unknown `--set` names are an error; unknown env vars
  are ignored; `$comment` in `defaults.json` is never a setting.
- **Derivation happens here and only here**: `<TYPE>_EVENTS` set (SMOKE, LOAD, STRESS, MATCHER_FLOOD) →
  `<TYPE>_DURATION` = `ceil(events / rate)` seconds, source `derived`, warning if a duration was also given
  explicitly (events win). `*_EVENTS` count **measured-phase** events (warm-up excluded).
  `STEP_SLA_MAX_WAIT=auto` → `2 × services.stepSla.pollIntervalSeconds`; `STEP_SLA_PEAK_ALARM_RATE=auto` →
  §3.2.
- `phasePlan` = `buildPhasePlan({ testType, settings: values, breakpointKind })` from `lib/phase-plan.js`
  (§4.1): the **same code** k6 uses. `buildPhasePlan` receives already-derived values and **never derives
  `*_EVENTS` itself**; it reads only durations and rates (and `STEP_SLA_STORM_ALARMS`). A1's unit tests pass
  pre-derived numbers; the `LOAD_EVENTS=1000 → LOAD_DURATION 20` test belongs to A2.
- `RUN_ID` is validated (§2.3) and the longest possible event id is checked against 50 characters.
- Thresholds read the same `values` (`HTTP_P95_LIMIT_MS`, …): there is no second threshold config.

k6 never reads env vars for settings: Node writes `results/<dir>/run-context.json` and passes
`-e RUN_CONTEXT=/tests/results/<dir>/run-context.json`. `lib/run-context.js` throws
`"RUN_CONTEXT missing: run tests through scripts/run-test.sh"` when absent.

### 3.4 Printed and saved

  (phase, rate, start, duration, planned events) and the docker command (secrets masked).
- Saved: `run-context.json` (§5.1) and `result.conditions.settings` (`{NAME: {value, source}}`).

## 4. Shared k6 library API (`lib/`, A1)

### 4.1 `lib/phase-plan.js` (PURE)
```js
/** @typedef {{name:'smoke'|'warm-up'|'measure', kind:'constant'|'staircase', rate:number, startSeconds:number,
 *             durationSeconds:number, plannedEvents:number, levels?: Level[]}} Phase
 *  @typedef {{rate:number, startSeconds:number, durationSeconds:number, plannedEvents:number}} Level
 *  @typedef {{testType:string, breakpointKind:'staircase'|'flood'|'none', phases:Phase[], measuredPhase:'smoke'|'measure',
 *             totalSeconds:number, plannedEvents:number, plannedMeasuredEvents:number, windowSeconds:number,
 *             windowCount:number}} PhasePlan */
export function buildPhasePlan({ testType, settings, breakpointKind = 'staircase' }) → PhasePlan
export function phaseAt(phasePlan, elapsedSeconds) → { phase, phaseIndex, level|null }
export function plannedSentBy(phasePlan, elapsedSeconds) → number   // events the schedule should have sent by t
```
| testType | phases |
|---|---|
| smoke | `smoke` constant `SMOKE_RATE` × duration (no warm-up); `measuredPhase` = `smoke` |
| load | `warm-up` (if `WARM_UP_DURATION` > 0) then `measure` constant `LOAD_RATE` |
| stress | `warm-up` then `measure` constant `STRESS_RATE` |
| breakpoint, `staircase` | `warm-up` then `measure` staircase over `LEVELS`, each `LEVEL_DURATION` |
| breakpoint, `flood` | `warm-up` then `measure` constant `MATCHER_FLOOD_RATE` × `MATCHER_FLOOD_DURATION` |
| smoke/load/stress, `none` (Step SLA) | `measure` only, constant `<TYPE>_RATE` × `<TYPE>_DURATION` (already derived from `<TYPE>_EVENTS` by settings, §3.3), used as the ring schedule; `startSeconds` = `STEP_SLA_FIRST_RING_DELAY`; `plannedMeasuredEvents` = the alarm count (the single source for Step SLA, §6.7) |
| breakpoint, `none` (Step SLA storm) | `measure` only, `rate: 0` (all ring at once), `durationSeconds: 0`, `plannedEvents = STEP_SLA_STORM_ALARMS`; `windowSeconds` = `REPORT_WINDOW` and windows then cover the catch-up period |

`windowSeconds` = max(`REPORT_WINDOW`, ceil(measure duration / 200)); windows cover the measured phase only.
Refining a staircase (warm-up at the last good level, D11): the runner sets `WARM_UP_RATE` = held level and
`LEVELS` = fine levels (§6.9), so no special phase kind is needed.
`settings` here is `ResolvedSettings.values` (§3.3): durations are seconds, `LEVELS` is `number[]`.
Phase kinds are `constant` and `staircase` only; a `profile` kind fed by `WORKLOAD_PROFILE` (spec 007) and
`EVENT_MODE=journey` are later work (§3.2 reserved settings).

### 4.2 `lib/thresholds.js` (PURE)
```js
export function allowedDropped(plannedEvents, maxDroppedRate) → number        // floor(planned × rate)
export function buildThresholds({ phasePlan, settings, kind: 'http'|'kafka' }) → k6 thresholds object
export function describeThreshold(metricKey, rule) → { metric, rule, description, unit }  // plain words for reports
export function isDummyRule(rule) → boolean   // true for 'count>=0', 'p(95)>=0', 'rate>=0' (summary-forcing rules, never reported)
```
Rules produced (`M` = sub-metric filter of the measured scenario, `{scenario:measure}` or `{scenario:smoke}`):
- warm-up/smoke sanity: `checks{scenario:warm-up}` `rate>MIN_CHECKS_RATE` with `abortOnFail: true`. Only added when the phase exists (`WARM_UP_DURATION=0s` → no warm-up scenario, no rule).
- http load/stress/smoke: `http_req_duration{M}` `p(95)<HTTP_P95_LIMIT_MS`; `http_req_failed{M}`
  `rate<HTTP_MAX_FAILED_RATE`; `checks{M}` `rate>MIN_CHECKS_RATE`;
  `dropped_iterations` `count<=allowedDropped(plannedEvents, MAX_DROPPED_RATE)`.
- http stress additionally: `http_req_failed{scenario:measure}` `rate<0.10` abortOnFail, delayAbortEval `10s`.
- http breakpoint: per level `R`: `http_req_duration{level:R}` p95, `http_req_failed{level:R}`,
  `checks{level:R}` (all abortOnFail, delayAbortEval `10s`) and `iterations{level:R}` `count>=0`
  (forces the sub-metric into the summary); `dropped_iterations` `count<BREAKPOINT_MAX_DROPPED` abortOnFail.
- kafka (matcher): `kafka_writer_error_count` `count<=MATCHER_MAX_KAFKA_WRITE_ERRORS`; `checks{M}`;
  `dropped_iterations` `count<=allowedDropped(…)`. Backlog/catch-up rules are evaluated by the Node watcher.
- event counters (all k6 tests): `events_sent{scenario:M}` `count>=0` and `events_accepted{scenario:M}`
  `count>=0` (dummy rules so the measured-phase counts appear in the summary; counters defined in
  `lib/event-metrics.js`, §4.7).
- windows (all k6 tests): for each window `i`: `iterations{window:i}` `count>=0`, and for http
  `http_req_duration{window:i}` `p(95)>=0`, `http_req_failed{window:i}` `rate>=0` — dummy rules that only
  make the per-window numbers appear in the summary for breaking analysis.

### 4.3 `lib/scenarios.js` (PURE)
```js
export function buildScenarios(phasePlan, { exec = 'default', maxVus }) → options.scenarios
export function buildOptions({ context, kind }) → { scenarios, thresholds, summaryTrendStats, tags, noConnectionReuse:false }
```
- Scenario names: `smoke`, `warm-up`, `measure` (constant-arrival-rate, `timeUnit: '1s'`, `startTime`
  from the phase); staircase `measure` = `ramping-arrival-rate`, `startRate` first level, stages per level
  `{duration:'1s', target:R}, {duration:(L-1)+'s', target:R}`.
- VUs, `kind: 'http'`: `preAllocatedVUs = clamp(ceil(rate × 0.5), 2, MAX_VUS)`, `maxVUs = clamp(max(ceil(rate × 4), 50), 2, MAX_VUS)`.
  Staircase: `preAllocatedVUs` from the **first** level, `maxVUs` from the **top** level (200→6400: 100 / 2000).
- VUs, `kind: 'kafka'`: every VU owns one librdkafka producer, so `preAllocatedVUs = min(KAFKA_PRE_ALLOCATED_VUS,
  max(2, ceil(rate × 0.5)))`, `maxVUs = clamp(ceil(rate × 4), preAllocatedVUs, KAFKA_MAX_VUS)` (flood 2000/s →
  100 / 500 = v1; smoke 1/s → 2 / 4); never
  derived from `MAX_VUS`. Smoke/warm-up phases use the same formulas with their own (small) rate.
- `summaryTrendStats: ['avg','min','med','max','p(90)','p(95)','p(99)']`.
- `tags`: `{ testid: runId, service: subject, test_type, plan_definition_set, environment }` (same names
  as the Prometheus labels, §9.3).

### 6.2 `run` lifecycle (`tools/commands/run-test.mjs`)
1. `loadEnvironment(env)` (refuse prod); `getServiceModule(subject)`; check `testType` ∈ module `testTypes`.
2. `resolveSettings(...)`; create results folder; write `run-context.json`; print settings + phase plan +
   docker command. `--dry-run` stops here (exit 0).
3. `runPreflight({ environment, subjects:[subject], settings, planDefinitionSetName })` → `preflight.json`;
   required failure → exit 2 (unless `SKIP_PREFLIGHT=true`, recorded).
4. `captureConditions(...)` (host, `git rev-parse --short HEAD` + `git status --porcelain` read-only,
   data volume SQL §6.8, plan-definition snapshot via `getActivePlanDefinitions`).
5. `module.waitForIdle?.(ctx)` (exit 2 on `IDLE_TIMEOUT`).
6. `const prep = await module.prepare?.(ctx)` (Step SLA seeding). If `prep` is an object
   (`PrepareResult`, §6.4) the runner sets `ctx.times.measureStart`, `ctx.times.sendEnd`
   (`timing.source: 'seed'`), resolves `ctx.times.ready`, and uses `prep.plannedEvents` as
   `load.plannedEvents`; `prep.manifestFile` is listed in `artifacts`.
7. Start `startMetricsSampler(...)` and `startWatchers(module.watchers, ctx)`; Grafana annotation "start"
   (every run, k6 or seeded, §9.3).
8. If `module.kind === 'k6'`: `runK6(...)` and `startK6Clock(...)` (§6.3) together; the clock sets
   `ctx.times` and resolves `ctx.times.ready` once k6 reports running (after `setup()`). If k6 exits before
   the planned send end (abort, Ctrl-C, error), `ctx.times.sendEnd` = exit time and `sendEndedEarly: true`.
   Else (`seeded`): wait until `ctx.times.sendEnd` (last alarm rang).
   Watchers may call `ctx.abortLoad(reason)` → `stopK6()` (`docker kill --signal SIGINT k6-<runId>`, so
   k6 still writes its summary). Ctrl-C on the runner does the same, then continues to step 10 with status
   `aborted`.
9. Watchers continue until they report done (caught up, limit, or stall); stop the sampler. After k6
   exits, the result builder re-bases all times on `context.k6StartedAt` from `k6-summary.json`
   (authoritative; the live REST value is used only when the summary lacks it, `timing.source`
   records which).
10. `module.dataChecks(ctx)` → `data-checks.json`.
11. `buildResult(...)` → `validateResult` → `result.json`; `renderRunReport` → `report.md` and stdout.
12. If `BASELINE` set: `compareWithBaseline` → `baseline-comparison.json` + section in report.
13. Exit code per §5.7.

`--refine-from <resultDir>` (breakpoint only): reads that result's `levels`, takes `heldUpTo` = G and
`brokeAtRate` = B, sets `LEVELS = computeFineLevels(G, B)` and `WARM_UP_RATE = G` (warm-up at the last good
level) unless the tester set them; the result records `refinedFrom`.

### 6.5 Watchers
```js
// Watcher = { name, start(): Promise<void>, stop(): Promise<void>, whenDone(): Promise<WatcherOutcome> }
// WatcherOutcome = { name, file, samples, thresholds: Threshold[], breaking: Partial<Breaking>, load: Partial<Load> }
```
Watchers sample every `WATCH_INTERVAL`, append to `watch-<name>.json` as they go (so an abort keeps data),

### 6.6 Matcher backlog watcher (B2, `cce-matcher-service/watchers/backlog-watcher.mjs`)
- Every interval: `kafkaAdmin.getGroupLag({ groupId: kafka.matcherConsumerGroup, topic: kafka.inboundTopic })`
  → `backlog`; scrape matcher → `processed = sum(cce_events_matched_total) + cce_events_duplicate_total`,
  `processingSum/Count` (`cce_events_processing_duration_seconds_sum/_count`), `errors =
  cce_consumer_inbound_errors_total`; DLQ end offset total at start and end.
- Derived per sample: `processedPerSecond` (Δprocessed/Δt), `drainRate` (processedPerSecond while
  backlog > `MATCHER_MAX_BACKLOG`).
- Samples carry absolute times (`at`); `t` relative to `ctx.times.measureStart` is computed once
  `ctx.times.ready` resolves (and recomputed by the result builder from the authoritative k6 start).
- Done when `now ≥ sendEnd` and (`backlog ≤ 10` → `caughtUp: true, catchUpSeconds = now − sendEnd`) or
  `now ≥ sendEnd + limit` → `caughtUp: false, remainingBacklog, gaveUpAfterSeconds` (fixes the v1 bug, D19).
- Thresholds: `matcher.backlog` (max ≤ `MATCHER_MAX_BACKLOG`; load/stress/smoke), `matcher.catch-up`
  (caughtUp and ≤ `MATCHER_MAX_CATCH_UP`; load/stress/smoke), `matcher.dead-letters` (Δ DLQ ≤
  `MATCHER_MAX_DEAD_LETTERS`), breakpoint: `matcher.drain-rate` (median > 0, informational target
  ≥ `EXPECTED_HEADROOM × PEAK_RATE`).
- `waitForIdle`: `waitForMatcherIdle` (tools/core/idle.mjs): lag = 0 and `processed` flat for `IDLE_FLAT_DURATION`.
  The collector module uses the **same** helper before its runs (every collector event also feeds the matcher,
  and a draining matcher competes for the shared Postgres, lesson 10).
- Collector after-run info: data check `collector.downstream-backlog-left` (severity `info`) = matcher group lag
  when the collector run ends (`readMatcherBacklog`), so the report says "matcher still draining N events".

### 6.7 Step SLA seeding and watcher (B3)
- Test definitions `cce-step-sla-service/tests/step-sla-<type>.test.mjs` export
  `default { testType, describe(resolved /* ResolvedSettings incl. derived.phasePlan */) → { alarmCount, ratePerSecond, maxWaitSeconds, catchUpLimitSeconds } }`
  (no side effects at import). **`alarmCount = phasePlan.plannedMeasuredEvents` and `ratePerSecond =
  measured phase rate`, always read from the phase plan** (single source, §4.1); `describe()` adds only the
  wait/catch-up limits. smoke 30 at 1/s; load 30,000 at 50/s; stress 120,000 at 200/s; breakpoint (storm)
  `STEP_SLA_STORM_ALARMS` (100,000) at rate 0.
- `seeding/seed-alarms.mjs` `seedAlarms(ctx, plan) → PrepareResult` (the module's `prepare`): one transaction;
  pairs = `STEP_SLA_SEED_MODE=set` → every (plan definition of the set, ACTIVE by url+version) × each of its
  mandatory (`must`) actions, alarms assigned round-robin (alarm n → pair n mod P), one patient per alarm;
  `single-action` → the set's first plan definition + `STEP_SLA_ACTION_ID` (refused if not `must` there).
  SQL as archive/v1/seed-sla.sh with `patient_id = 'LOADTEST-<runId>-sla-0-' || n`, ids from `UUID_V7_SQL`
  (§2.3), ring = `now() + STEP_SLA_FIRST_RING_DELAY + (n−1)/rate`, DUE rows only unless
  `STEP_SLA_SEED_MISSED_ALARMS`, parameterised. Writes `seed.json` `{runId, alarmCount, ratePerSecond,
  ringStartMs, ringEndMs, seedMode, pairs:[{protocolDefinitionId, canonical, actionId, alarms}], missedSeeded,
  missedRingStartMs|null, seededAt}` into the results folder (D20) and returns `{ measureStart: ringStart,
  sendEnd: ringEnd, plannedEvents: alarmCount, manifestFile: 'seed.json' }`.
- Expectation: Step SLA rates are alarms/s; `× peak` uses `STEP_SLA_PEAK_ALARM_RATE` (§3.2), never `PEAK_RATE`.
- Watcher `watchers/alarm-watcher.mjs`: samples `cce_sla_transitions_due`, Δ(`applied_total +
  skipped_total`), `cce_sla_evaluator_cycles_total` (must increase: scheduler alive),
  `cce_sla_evaluator_batches_failed_total`; done when handled ≥ alarmCount or `now ≥ ringEnd + limit`;
  drain rate recorded while due > 1000 and **reported only for breakpoint** (lesson 6).
- `waitForIdle`: `cce_sla_transitions_due ≤ 0` for `IDLE_FLAT_DURATION`.
- Data checks (authoritative, from the DB; v1 report-sla SQL with the run prefix): handled = count;
  OVERDUE = count; deviations = count; wait avg/p95/max; `max < STEP_SLA_MAX_WAIT` (smoke/load/stress);
  breakpoint: catch-up (last processed_at − last ring) < `STEP_SLA_STORM_MAX_CATCH_UP`.
  "Started breaking" = `min(process_by)` of alarms whose wait > max wait.

### 6.8 Data checks and shared SQL
`DataCheck = { id, description, expected, actual, comparison, passed, severity, sql? }` (`sql` text kept
for transparency). **Index-friendly selection** (ccedb uses `en_US.utf8`, so a btree cannot serve `LIKE`,
and a parameterised `$1 || '%'` never can):
- Event tables (`inbound_event_log`, `matcher_event_log`): the candidate ids are generated from the phase

### 6.9 Breaking analysis (A2, `breaking-analysis.mjs` + `staircase.mjs`)
- **Windows (load/stress/flood, k6):** a window is broken when any of: `p95 > HTTP_P95_LIMIT_MS` (http),
  failed rate > `HTTP_MAX_FAILED_RATE` (http), checks < `MIN_CHECKS_RATE`, `iterations < (1 −
  RATE_SHORTFALL_TOLERANCE) × rate × windowSeconds` ("k6 could not send on time"). Started breaking = start
  of the first of `BREAK_CONSECUTIVE_WINDOWS` broken windows in a row; `secondsIntoMeasure` and clock time
  (clock = `measureStart` from the k6 clock contract + window start, never the docker start time).
  **k6 limit for windows too (D9):** when the only failed rules of the run are dropped iterations and/or
  shortfall windows and the measured p95 < `K6_LIMIT_P95_MS` → `breaking.k6Limited = true`, `whatBroke` says
  "k6 could not send N on time (k6 limit, service p95 X ms)", `statusReason` says the same, and the result is
  `failed` only on the k6 rule (the report labels it as a load-generator limit, not a service failure; the v1
  case of 11 dropped of 30,020 at p95 20 ms reads this way).
- **Staircase:** per level from `{level:R}` sub-metrics: broke if a level threshold failed, or iterations <
  (1 − tolerance) × planned. `heldUpTo` = highest level with nothing broken below or at it; `brokeAtRate` =
  lowest broken level; `startedBreakingAt` = that level's start. If the run's `dropped_iterations` rule
  failed with no level broken, the top level reached is marked broken with reason "k6 dropped N".
  **k6 limit (D9):** broken only by shortfall/dropped while p95 < `K6_LIMIT_P95_MS` → `k6Limited: true`,
  report "at least <heldUpTo or level>/s (k6 limit)".
- **Backlog series (matcher):** first sample in the measured phase with backlog > `MATCHER_MAX_BACKLOG`
  for `BREAK_CONSECUTIVE_WINDOWS` samples.
- **What broke** list: each failed rule turned into words by `describeThreshold` (e.g. "p95 666 ms (rule
  < 500 ms)", "N requests k6 could not send on time", "up to N events waiting (rule < 1,000)", "not caught
  up: N events still waiting after 120 s").
- **Dropped iterations**: exact count, share, allowed count, and whether it decided the verdict.
- **Diagnostics**: `diagnosticsNear` adds `whatBroke` entries with `source: 'service-metrics'` for every
  `PEAK_SIGNALS` signal whose `firstAt` lies within ±1 window of `startedBreakingAt` (e.g. "collector DB pool:
  requests waiting for a connection from 14:31:02", "Step SLA hit the 10,000-rows-per-cycle cap"). They
  explain; they never change the verdict.

### 7.2 Cleanup tables (child first; `tools/cleanup/cleanup-tables.mjs`)
**One connection.** `runCleanup` checks out ONE dedicated client (`withDedicatedClient(pool, …)` or a
`pg.Client`) for the whole cleanup and never uses `pool.query`: the `lt_*` TEMP tables, `SET` and
`CREATE INDEX CONCURRENTLY` are all session-bound. No other connection of the tool is open while it runs
(preflight-style checks run before, on the same client). Cleanup resolves settings with
`resolveSettings({ environment })` (no subject/test type).

**Selectors** (`$sel` = one of `runSelectors(runId)`: `LOADTEST-<runId>-col-`, `-mat-`, `-sla-`, ORed; `--all`:
`LOADTEST-`). Bounds when the run start is known (`runIdStart(runId)` for default ids, or `startedAt` from
the run folder's `run-context.json` found by `findResultDirs`): `$floor = uuidV7Floor(runStart − 5 min)`;
when the run's `run-context.json` exists, event tables use the generated candidate ids (§6.8). Without a
known start (custom id, no run folder, `--all`) the stage scans whole tables; the printed plan and the JSON
say so ("full scan: may take minutes on large tables").

Stage (one session, read-only scans, TEMP tables with primary keys + `ANALYZE`):

Batch delete per table, on the dedicated client, each batch its own explicit transaction (`SET LOCAL`
only works inside one), looping until a batch deletes 0 rows:
```sql
BEGIN;
SET LOCAL lock_timeout = '<CLEANUP_LOCK_TIMEOUT>s';
WITH b AS (DELETE FROM lt_x WHERE id IN (SELECT id FROM lt_x LIMIT $n) RETURNING id)
DELETE FROM <table> t USING b WHERE t.id = b.id;
COMMIT;            -- on lock_timeout: ROLLBACK, pause, retry the batch (max 5), then status 'incomplete'
```
Between batches: pause `CLEANUP_PAUSE`; every 10 batches check slots (`wal_status`, `safe_wal_size`) and
free disk (`disk.data-stores` rule, §7.1); stop with status `incomplete` (counts saved) if a slot is not
`reserved`/`extended` or `safe_wal_size` < `CLEANUP_MIN_SAFE_WAL_GB`.

Temp index (`CLEANUP_TEMP_INDEX`), on the **same client with no transaction open** (the tool holds no
other connection, so `CONCURRENTLY` cannot wait on the tool itself):
1. `SELECT indisvalid FROM pg_index WHERE indexrelid = to_regclass('loadtest_cleanup_matched_event')` — an
   INVALID leftover (from an interrupted earlier run) is dropped first with `DROP INDEX CONCURRENTLY`
   (`IF NOT EXISTS` would silently keep an invalid index).
2. `CREATE INDEX CONCURRENTLY IF NOT EXISTS loadtest_cleanup_matched_event ON step_instance (matched_event_id) WHERE matched_event_id IS NOT NULL`
   before table 11; check `indisvalid` again (invalid → drop, fall back to small batches).
3. `DROP INDEX CONCURRENTLY IF EXISTS loadtest_cleanup_matched_event` in a `finally` (never the v1
   in-transaction `CREATE INDEX`). Without the index, table 11 uses batches of 500.

Guards (all recorded in `guards`): not prod; `safety.allowCleanup`; database name matches; run id is not a
prefix of another run's id in `results/` (§2.3); **refuse while processing**, scoped to this run's data:
- staged unprocessed transitions already due (`SELECT count(*) FROM step_sla_state_transition t JOIN lt_si s
  ON t.step_instance_id = s.id WHERE NOT t.is_processed AND t.next_attempt_at <= now()`) > 0;
- `kind: local`: matcher consumer-group lag > 0 (the laptop has no other traffic);
- `kind: dev/uat` (real traffic keeps lag above 0): instead, no new `matcher_event_log` / `protocol_instance`
  rows for this run's selectors during `IDLE_FLAT_DURATION` (two counts `IDLE_FLAT_DURATION` apart; `--all`:
  uses the `LOADTEST-` selector with the UUIDv7 bound of the last hour);
- `--wait` waits up to `IDLE_TIMEOUT` for these;
free disk ≥ `MIN_FREE_DISK_GB` (`disk.results` and `disk.data-stores`); slot health; interactive
confirmation (typed `yes`) unless `--yes`.

Modes: `--print-sql` (no connection: prints every statement), `--dry-run` (connects, stages, counts,
`ROLLBACK`, writes JSON with `mode: dry-run`), delete. **Verification** (two independent checks per table):
- `afterBySnapshot` = `SELECT count(*) FROM <table> WHERE id IN (SELECT id FROM lt_<x>_all)` — rows staged
  before deleting that still exist;
- `afterByPredicate` = the **direct** predicates against base tables with no join through already-deleted
  parents: `patient_id`/`subject` `LIKE $sel` on protocol_instance, intelligence_event_log and
  intelligence_delivery; the candidate-id / `cloudevents_id` selectors (and the legacy JSONB branches when
  active) on the event tables; for child tables without an own selector (step_instance,
  step_instance_history, protocol_instance_history, step_sla_state_transition, deviation,
  step_group_instance) **orphans**: rows whose parent id is in `lt_pi_all`/`lt_si_all` (catches rows written
  mid-cleanup, e.g. history rows Step SLA added; those tables have no FK);
- `after` = `afterBySnapshot + afterByPredicate`; status `verified` only when every `after` is 0. Any
  orphans found are deleted in one more batch round and re-verified once.
Then `ANALYZE` the touched tables and note "autovacuum will follow; preflight warns until it finishes". Output: the JSON (§5.6) into the run folder as `cleanup-<yyyymmdd-hhmmss>.json` (found by `runId` via `findResultDirs`) or
`results/cleanup-<runId|all>-<yyyymmdd-hhmmss>/cleanup.json`, plus a printed table
`order · table · before · deleted · after`.

3. **Load-test marker**: `load` adds `meta.tag: [{ "system": "http://openphc.org/fhir/CodeSystem/cce-performance-tests", "code": "loadtest" }]`
   to the PlanDefinition it posts (standard FHIR; `generate` output and the A3 equality test are unaffected).
   `retire`/`delete` first `GET` the definition and refuse any that lacks the marker ("not loaded by this tool:
   left untouched"), even when it belongs to the named set. A definition loaded by v1 (no marker) is therefore
   never retired/deleted by the tool; the message says how to do it by hand if really intended.
4. Ledger (informational): every write is appended to `.cache/plan-definitions/<env>-ledger.json`
   `{at, action, canonical, id}`; `status` shows it. The marker, not the ledger, is authoritative.
**Never** retire or delete a plan definition that is not part of the named set (no v1 `--retire-others`).
Note for Dev/UAT (open question Q3): even a suffixed test definition has the same triggers as the real one,
so while it is ACTIVE it also matches real events there; loading sets on shared envs needs team agreement.

### 8.2 Series report (`report --series …` → `summary.json` + `summary.md`)
`summary.json` (`kind: cce-performance-summary`, `schemaVersion 1.0.0`): `{ generatedAt, runs:[{dir, subject,
testType, status}], expectation:{ peakRate, loadTarget, stressTarget, headroom }, services:[{ subject,
load:{…}, stress:{…}, breakpoint:{…} }], wholeFlow:{…}, bottomLine:{…}, conditionsDiffer:[…] }`.
Markdown sections:
1. **What we expect** — peak, load = 1× peak, stress = `EXPECTED_HEADROOM`× peak, the rules (TBC marked).
2. **Load** table — service · events through · in (interval) · average rate · result · notes.
3. **Stress** table — service · events through · started breaking (clock, s in) · what broke · result.
4. **Breaking points** — service · held up to · broke at · when · × peak · vs expected (above/below by N/s);
   matcher = drain rate (events/s); Step SLA = drain rate (alarms/s, storm only; × peak against
   `STEP_SLA_PEAK_ALARM_RATE`, never the events/s peak).
5. **Whole flow** — weakest link = min(collector held, matcher drain rate) in events/s with its × peak;
   "end-to-end module not built yet: see archive/README.md" until an `end-to-end` module result exists.
6. **Data correctness** — every required data check passed? (sent = stored = processed = enrolled).
7. **Bottom line** — load passed X/Y, stress X/Y, capacity vs target, baseline verdicts if any.
8. **Conditions** — one block; a warning list when runs in the set had different conditions.
Missing runs show "not run". Old v1 folders (no result.json) are ignored.

Metric keys come from each module's `baselineMetrics(result)`; at least:
collector `{load,stress}.p95Ms`, `{load,stress}.averageRate`, `breakpoint.heldUpTo`, `breakpoint.brokeAtRate`;
matcher `load.maxBacklog`, `load.catchUpSeconds`, `stress.processedPerSecond`, `stress.maxBacklog`,

Rules:
- **Save**: each (subject, testType) included needs ≥ `BASELINE_MIN_RUNS` (3) runs with status `passed` or
  `failed` (not `error`); fewer → refused unless `--allow-fewer` (then `provisional: true`, shown in every
  comparison). Runs must share environment, plan-definition set, dataset and rate/duration settings, else
  refused with the differences listed. Existing name → refused unless `--force`.
- **Compare**: current value = mean of the given runs' values. Same (`≈`) if `|Δ| <` unit floor
  (`ms` 5, `s` 2, `events` 100, `events/s` 5, `alarms/s` 20) or `|Δ%| ≤ BASELINE_TOLERANCE`; else better

  → "not caught up" (never a number).
- **Condition warnings**: environment, host name/cpus, k6 image, plan-definition set/fan-out/canonicals,
  dataset, any compared setting, data volume (DB size or any main table differing > 50 %), suite commit.
- Output: `baseline-comparison.json` `{ baseline, provisional, tolerance, warnings:[…], rows:[{key, label,
  unit, baseline, current, delta, deltaPercent, verdict:'better'|'worse'|'same'|'not-compared'}] }`;
  comparison never changes a run's status (informational).
- Baseline files are written with a generated `$comment` header (§2.4) and the loader drops it.

### 10.4 How an adaptor or end-to-end module plugs in later (independent)
- Adaptor: new folder named after its repository (e.g. `openhim-cce-emitter-adaptor/`, `tiberbu-adaptor/`)

  its own dataset if the EMR payload differs. The registry finds it automatically; no shared code changes
  except adding its health/metrics key metric to preflight's table (data-driven: the module declares
  `preflightMetric`). The v1 OpenHIM test in `archive/v1/adaptor/openhim.js` is the reference.
- End-to-end: folder `end-to-end-flow/` with a module (`subject: 'end-to-end'`), journeys from the dataset

  stage SQL, threshold event → enrolment p95 < 10 s; the series report's "whole flow" section then uses its
  result instead of the weakest-link estimate.
